# Languages: English, 日本語, Español

Every page with the rail can be read in Japanese or Spanish. The choice is the last row of the
rail's foot (bottom-left on a desktop, the bottom of the phone's menu sheet), is kept on the
device (`localStorage epinoia_lang`), and can be set by a link: `?lang=ja`, `?lang=es`,
`?lang=en`.

| file | what it is |
|---|---|
| `epinoia/i18n.js` | the engine and the language registry (`LANGS`), loaded synchronously in `<head>` on every page |
| `epinoia/i18n/ja.js`, `es.js` | the core dictionaries (the rail, stats vocabulary, public pages), fetched only for that language |
| `epinoia/i18n/<code>/<pack>.js` | packs: the words of one area, fetched only by the pages that name them (`data-i18n-packs`) |
| `epinoia/nav.js` (`lang-row`) and `kit/nav.css` | the picker |
| `tools/i18n.mjs` | every job on the language files, as commands (below) |
| `supabase/tests/i18n.test.mjs`, `i18n-tool.test.mjs` | engine, wiring, parity across every language, packs, the precedent below, the tool |
| `tools/i18n-coverage.mjs` | which English strings in the source have no translation yet, per area |

## The commands

    node tools/i18n.mjs status                      what every language and pack still lacks
    node tools/i18n.mjs add entries.json            new or corrected strings, every language at once
    node tools/i18n.mjs remove <pack> <section> <english>
    node tools/i18n.mjs new-pack <name> <page/>...  a new area's pack, and its pages wired to it
    node tools/i18n.mjs new-language fr --native Français --short FR --locale fr-FR --decimal ,
    node tools/i18n.mjs export fr --out fr.json     the worklist: every key, the other languages beside it
    node tools/i18n.mjs import fr fr.json
    node tools/i18n.mjs unhide fr                   into the picker, once complete

A new language starts **hidden**: it is out of the picker, still reachable with `?lang=fr` for
checking, and the tests only warn about what it lacks. `unhide` puts it in the picker, after
which the tests hold it to every key like the others. The Claude skill `epinoia-languages` runs
these recipes end to end: "add French", "translate the admin console", "the Spanish says X".

| pack | pages |
|---|---|
| core | every public reader page (HOME, league pages, fixtures, table, stats, scouting, clubs, players, injuries, games, news) |
| `game` | the box score page, the video hub |
| `report` | generated prose: match reports, previews, facts, the injury wire, weekly reports, auto news articles |
| `account` | profile, sign in, contact, join, invite |
| `info` | learn, privacy, API docs, the app pages, countries |
| `admin` | the league console |
| `platform` | the platform console, access plans, club portal, editor |
| `scorer` | the scoring app, clock cam |
| `broadcast` | the on-air overlay, the control room, its help |
| `embed` | every widget and the gallery; a host site picks the language with `data-lang` |

## How a page is translated

English costs nothing: no dictionary is fetched, nothing is observed, dates are untouched.

For Japanese or Spanish, `i18n.js` hides the body, fetches the dictionary, translates what is
already on the page, then watches the DOM (a `MutationObserver`) so everything a page renders
later is translated before it is painted. If the dictionary does not arrive within 2.5 s the
page shows in English rather than staying blank.

It translates **by the English text itself**, so no page had to be rewritten to use keys. That
is also why it is careful:

* **Context first.** The same letters mean different things in different places. Inside a
  table header (`th`) the `col` context applies; in a header row that also has a `PA` column,
  `standings` applies too, so `PF` is points for (Spanish `PF`, Japanese `得点`) there and a
  personal foul (`Fp`, `F`) everywhere else. The rail (`nav`) and the phone bar (`tab`, which
  gets shorter labels) are contexts, and any element can declare one with
  `data-i18n-ctx="col"` (the stats table's column picker does).
* **Names are left alone.** Only strings in a dictionary change. League and club names in the
  rail are marked `translate="no"`, as is anything under `.notranslate` or `data-i18n="off"`.
  Mark a container `translate="no"` if a name ever collides with a dictionary word.
* **Case follows the page.** `fixtures` → `calendario`, `FIXTURES` → `CALENDARIO`.
* **Composites are taken apart.** `Fixtures · Epinoia` is translated either side of the dot;
  `leagues ›` keeps its arrow; `3 games` uses the `units` table; `Q4`, `W3`, `Leagues in Spain`,
  `50 of 61 players` use `patterns`.
* **Dates** everywhere come from `toLocale*String('en-GB', …)`; asked for English, those now
  answer in the chosen language (`9月26日(土)`, `sáb, 26 sept`).
* **Numbers** take a decimal comma in Spanish (`45,5%`, `8,0-19,0`), as Spanish stat tables
  print them. A version (`1.0.0`) or a clock's tenths (`0:05.4`) is left alone.

Japanese text is set in the system's Japanese face behind the pixel fonts (none of the four
bundled fonts has kana or kanji); the rail's labels are larger and untracked in Japanese.

## What the words are based on

The user's instruction was to follow precedent, not a dictionary: the words the leagues
themselves print, and basketball media in each language. Sources, read 2026-09-23:

* Japanese: B.LEAGUE's game pages (box score, live text, report), standings, stats and leaders,
  glossary (`bleague.jp/glossary/`), rules page and player pages; basketballking.jp match reports.
* Spanish: ACB's live game pages (`live.acb.com`: estadísticas, jugadas, resumen, estadísticas
  avanzadas), standings, calendar, team and player pages and news; FEB's live game pages and
  rankings; Spanish-language media for prose.

These names appear here only. The shipped files describe the conventions ("as Spanish
standings write it") without naming a site, as with every other EPINOIA source
(`i18n.test.mjs` checks).

### Elsewhere

* Periods: `1Q`–`4Q`, `OT1` (ja); `1C`–`4C`, `PR1` (es).
* Live text: `3Pシュート○` / `3Pシュート×` (made ○, missed ×); `Triple anotado` / `Triple fallado`.
* Tabs: レポート, ボックススコア, テキスト速報, スコアチャート; Crónica, Estadísticas, Jugadas.
* A lone `v` between two clubs: `VS` (ja), `vs` (es). A crest monogram `V` is not touched.
* HOME, the front page, is `トップ` / `Inicio`; the home side is `ホーム` / `Local`.
* Time to be confirmed: `時間未定` / `--:--`.
* Player lines on cards: `23.3得点 6.3リバウンド 4アシスト` / `23,3 Pts 6,3 Rt 4 As`.

## What stays English, on purpose or for now

* **Names**: players, clubs, leagues, venues. Japanese league sites write foreign players in
  katakana, but transliterating names automatically would get people's names wrong. Where a
  feed already gives a katakana name, that is what shows.
* **Product and data words**: brands (FIBA LiveStats, OBS, vMix, Stripe, YouTube), keyboard keys,
  typed scorer commands, import/export column headings the importer only reads in English,
  CSV/JSON/ZIP contents, slugs, emails and raw server errors.
* **Advanced stats** (TS%, USG%, BPM, RAPM…), as both leagues print them.
* **Notifications** (email and push) are written by the server in English. A per-account
  language (`fan_prefs.lang`) would let the notify function write in it; that needs a migration.
  Server messages shown in the bell and the notification kinds are English for the same reason.
* **The printed scoresheet** and the clock cam's canvas box labels: the first is written into a
  separate iframe, the second drawn on a canvas; neither passes through the page the engine
  watches. `<meta>` descriptions (social previews) stay English too.
* The browser's own language does not switch the site automatically. To make it do so, change
  `pick()` in `i18n.js` to fall back to `navigator.language` before `'en'`.

Everything else — every page with the rail, both consoles, the club portal and editor, the
scorer, the broadcast overlay and control room, the embeds, and the generated prose (match
reports, half-time reports, previews, the injury wire, weekly reports, auto-written news) — is
covered in both languages. `node tools/i18n.mjs status` shows the counts.

## Adding a string

Write the English exactly as the page shows it, with every visible language, in an entries file,
and run `node tools/i18n.mjs add entries.json`:

    [{ "pack": "core", "section": "phrases",
       "entries": { "shot clock analysis": { "ja": "ショットクロック分析", "es": "Análisis del reloj de posesión" } } }]

`section` is `phrases` (any case matches), `ctx.<name>` (the meaning depends on where it is:
`ctx.col` a column header, `ctx.tab` the phone bar), `units` (for "3 games") or `exact`.
Patterns for text built from pieces are written by hand in the files.

To find what is still English on a real page, open it with `?lang=ja&i18n=misses`, use it,
then run `EpinoiaI18n.misses()` in the console: every string the engine saw and could not
translate, most frequent first (names included). `node tools/i18n-coverage.mjs ja --only <page/> --pack <pack>`
does the same from the source, more roughly.

## Adding a language

    node tools/i18n.mjs new-language fr --native Français --short FR --locale fr-FR --decimal ,
    node tools/i18n.mjs export fr --out fr.json      then fill every "fr"
    node tools/i18n.mjs import fr fr.json
    node tools/i18n.mjs status                       until every pack is complete
    node tools/i18n.mjs unhide fr

Before the first word: research what that language's box scores, standings and media print
(the same precedent rule), check the bundled fonts cover its letters, and write the sentence
patterns in its own word order. The skill's new-language reference has the checklist.
