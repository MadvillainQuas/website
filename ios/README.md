# Epinoia for iPhone

The Epinoia iPhone app is a **native Swift/UIKit shell around a full-screen WKWebView**. It opens
the live website, `https://prophesyscouting.co.uk/epinoia/home/?source=ios`, and adds the native
parts a website can't have inside iOS:

- **notifications through Apple Push Notification service** (WKWebView has no Web Push), asked for
  in context by the site, never at launch
- its own icon, and a launch screen in HOME's colour (`#f3faf6`)
- universal links: `https://prophesyscouting.co.uk/epinoia/...` opens in the app
- native `alert()`, `confirm()` and `prompt()` dialogs, downloads through the share sheet, and a
  native "You're offline" screen

Website changes never need a new app. The app shows whatever the site serves on its next load.
A new build is only needed when something in this folder changes.

The name people see is **EPINOIΛ** (`CFBundleDisplayName`, the dialogs, the offline screen). The
target, the scheme, the module and every file stay `Epinoia`.

| | |
|---|---|
| Bundle ID | `uk.co.prophesyscouting.epinoia` (the same as the Android package) |
| Host | `prophesyscouting.co.uk` (the apex, never `www`) |
| Version | read from `../epinoia/ios/version.json` (`build`, `version`) by CI |
| Devices | iPhone only (`TARGETED_DEVICE_FAMILY` 1), portrait and both landscapes |
| Deployment target | iOS 16.0 |
| Swift | language mode 5, minimal concurrency checking (UI types are `@MainActor`) |
| Xcode | newest stable on GitHub's `macos-26` image (App Store uploads need Xcode 26) |
| Project | generated by [XcodeGen](https://github.com/yonaskolb/XcodeGen) from `project.yml`, never committed |
| Dependencies | none: UIKit, WebKit, UserNotifications |

## What's in here

```
ios/
  project.yml                    XcodeGen spec: one target, one scheme, all build settings
  .gitignore                     the generated .xcodeproj, build output, signing files
  Epinoia/
    AppDelegate.swift            entry point; notification centre delegate; APNs token callbacks
    SceneDelegate.swift          the window; universal links; badge and status on every return
    WebViewController.swift      the web view: navigation policy, dialogs, downloads, theme colour,
                                 pull to refresh, offline screen, process-crash reload
    NativeBridge.swift           window.EpinoiaNative, the "epinoia" message handler, the events
    Push.swift                   notification permission, registration, the device token
    AppRouter.swift              holds a cold-start notification tap or link until the web view exists
    OfflineView.swift            "You're offline" / Try again
    Site.swift                   the host, the start URL, the URL tests, HOME's colours, the payload
    Info.plist                   written by hand (GENERATE_INFOPLIST_FILE is NO)
    Epinoia.entitlements         aps-environment production; applinks:prophesyscouting.co.uk
    PrivacyInfo.xcprivacy        the privacy manifest (see below)
    Assets.xcassets/
      AppIcon.appiconset/        one 1024 px icon, RGB, no alpha, square corners
      LaunchLogo.imageset/       the launch mark, 200 pt, 1x/2x/3x
      LaunchBackground.colorset/ #f3faf6, light and dark
```

The project was written by hand. The `.xcodeproj` is not committed: its `project.pbxproj` is
thousands of lines of generated IDs nobody can review, and it cannot be produced on the Windows PC
this repo is edited on. `project.yml` is the source; CI and a Mac both run `xcodegen generate`.

## The icon

Every PNG is generated from `brand-source/mark.png` by `tools/build-brand-icons.py`, with the
same script that draws the Android and web icons, so the iPhone app, the Android app and the web
app's icons share one blue. It writes the App Store icon, the launch mark and the download page's
`epinoia/ios/icon-192.png` and `icon-384.png`. The store icon is a full square: iOS applies its own
corner mask everywhere, and App Store Connect rejects a 1024 px icon with an alpha channel
(ITMS-90717), so it is saved as plain RGB. CI checks both.

To change the logo, replace `brand-source/mark.png`, run the script from the repository
root (`python tools/build-brand-icons.py`, needs numpy and Pillow), raise `build` in
`epinoia/ios/version.json`, and push. A new icon only reaches phones in a new build.

## How notifications work

1. The site asks. When someone turns game alerts on, `epinoia/push.js` calls
   `EpinoiaNative.call('push.enable')`. The first time, iOS shows its own dialog (it only ever does
   once); after that the app just registers again.
2. The app registers with APNs and gets the device token (`Push.swift`), and answers the call with
   `{permission, token, apnsEnv}`.
3. The site saves the phone as the endpoint `apns:<apnsEnv>:<token>` (migration 0130).
4. `notify` sends to that endpoint through APNs (`supabase/functions/_shared/apns.js`, with the
   server's own APNs key in the `APNS_*` function secrets, see docs/notifications.md §8). That key
   is not one of the CI secrets below.
5. A notification arriving while the app is open is shown as a banner with its sound, and the page
   gets a `push` event (the site's "check this phone" test waits for it). A tapped notification
   opens its `url`.

### The bridge: the contract with the website

`epinoia/push.js`, `epinoia/appmode.js` and `epinoia/nav.js` depend on every name here. Changing
one is a change on both sides.

**`window.EpinoiaNative`**, defined by a `WKUserScript` at document start, main frame only, in the
page content world, and only when `location.origin === 'https://prophesyscouting.co.uk'`:

```
{
  platform:   'ios',
  build:      <number, CFBundleVersion>,
  version:    '<CFBundleShortVersionString>',
  permission: 'default' | 'granted' | 'denied' | 'provisional' | 'ephemeral',
  token:      '<lower-case hex APNs device token>' | null,
  apnsEnv:    'production' | 'sandbox',
  call(name, args) -> Promise<object>
}
```

- `permission` is iOS's `UNAuthorizationStatus` when the page loaded (`notDetermined` is
  `'default'`). `token` is the last token Apple gave this install (kept in UserDefaults), or null.
- `permission` and `token` are writable; the app updates them. Everything else is read-only, the
  object is sealed, and `window.EpinoiaNative` itself cannot be replaced.
- `apnsEnv` is `'sandbox'` in DEBUG builds (run from Xcode), `'production'` otherwise.
- The values are JSON-encoded by `JSONSerialization` into the script, never pasted in as text.

**`call(name, args)`** posts `{name, args}` to `window.webkit.messageHandlers.epinoia`, a
`WKScriptMessageHandlerWithReply`, so it returns a Promise. The app **rejects** it with
`"not allowed"` unless the message comes from the main frame of `https://prophesyscouting.co.uk`
(port 0 or 443). Otherwise it always resolves with an object; failures are in its `error` string.

| name | resolves with |
|---|---|
| `push.status` | `{permission, token, apnsEnv}`, the status read from iOS now |
| `push.enable` | `{permission, token, apnsEnv, error?}`. Asks iOS if never asked; if notifications are allowed (authorized, provisional, ephemeral), registers and waits up to 15 s for the token. A cached token is answered if Apple is slower, with no error; `error` is set only when there is no token at all, or iOS failed. |
| `settings.open` | `{ok: true}` after opening this app's page in Settings > Notifications |
| `app.info` | `{build, version, systemVersion, model: 'iPhone'}` |
| anything else | `{error: 'Unknown method: <name>'}` |

Before resolving `push.status` and `push.enable`, the app also sets `EpinoiaNative.permission` and
`.token` to the values in the reply.

**Events** on `window`, `'epinoia-native'`, always after `EpinoiaNative.permission` and `.token` have
been brought up to date:

| `event.detail` | when |
|---|---|
| `{type: 'permission', permission, token}` | the page's values are stale: sent when the app returns to the foreground, or when a token arrives late while the app is open. Never while a `push.status` / `push.enable` call is in flight (its reply carries the news), never twice for the same values. |
| `{type: 'push', tag, kind, shown: true, opened: false, at}` | a notification arrived while the app is open (it is also shown as a banner) |
| `{type: 'push', tag, kind, shown: true, opened: true, at}` | a notification was tapped; sent after its `/epinoia` page has finished loading, or at once when its url opened outside the app |

`at` is when the app saw the notification, in milliseconds since 1970. `tag` and `kind` are null
when the payload has none.

**The APNs payload** the server sends has three custom keys beside `aps`, at the top level:
`url` (an https URL to open on tap), `tag` and `kind`. A tapped `url` on
`prophesyscouting.co.uk` under `/epinoia` loads in the web view (on a cold start it is held until
the web view exists, and replaces HOME); any other url opens in Safari.

**`epinoia://notification-settings`**: the site's "Open notification settings" link inside the app.
The web view never loads it; the navigation policy cancels it and opens this app's page in
Settings. (Android's equivalent is the `intent://` URL in `android/README.md`.)

**User agent**: WebKit's own, with `Mobile/15E148 EpinoiaApp-iOS/<build>` as the application name, so
the site can recognise the app before `window.EpinoiaNative` is read.

## Links: what stays in the app

| link | goes to |
|---|---|
| `https://prophesyscouting.co.uk/epinoia...` | the web view |
| `http://prophesyscouting.co.uk/...` | upgraded to https, then as above |
| the rest of `prophesyscouting.co.uk`, and every other site | the **Safari app** |
| `target=_blank` / `window.open` | an `/epinoia` page replaces the current page; anything else, Safari |
| `apps.apple.com`, `itms-apps:` | the App Store app |
| `mailto:`, `tel:`, `sms:` | Mail, Phone, Messages |
| `about:blank`, `blob:`, `data:`, embedded frames | loaded as they are |

**There is no in-app browser (no `SFSafariViewController`).** A browser inside the app that can
reach any site makes App Store Connect's "unrestricted web access" age-rating question a yes, which
rates the app 17+. Everything that leaves `/epinoia` leaves the app.

The camera is allowed for this site only (WebKit asks the person); the microphone is always refused,
because the app declares no microphone usage.

## Universal links

`Epinoia.entitlements` claims `applinks:prophesyscouting.co.uk`. The site side is
`/.well-known/apple-app-site-association` (no extension). It names the app as
`<Team ID>.uk.co.prophesyscouting.epinoia`, so it is written once the Apple Developer account exists,
by `node tools/ios-team.mjs <TEAM_ID>` (docs/ios-app.md, step 10). It claims `/epinoia/*` except
the pages that are never a person's page to read (embeds, broadcast overlays, the API docs, the dev
feed), and nothing outside `/epinoia`: the rest of the site is not the app.

iOS fetches the file through Apple's CDN when the app is installed, over https with no redirects
(hence the apex, never `www`). The app opens an `/epinoia` link whether it launched the app or
arrived while it was running (`SceneDelegate`); any other link iOS hands over goes on to Safari.

## The privacy manifest

`PrivacyInfo.xcprivacy` declares no tracking and no tracking domains. The one "required reason" API
the native code uses is UserDefaults, for the app's own state (the last push token, CI's start-URL
argument): reason `CA92.1`. Collected data is what the website collects when someone signs in: the
**email address** and the **user ID**, both linked to the person, neither used for tracking, both for
app functionality. The App Store privacy labels in App Store Connect must say the same. The file has
no comments on purpose: it is copied into the app as it is and parsed by App Store Connect.

## How CI builds it

`.github/workflows/ios.yml` (outside this folder) does everything, on `macos-26` with the newest
stable Xcode. On every push that touches `ios/`, `epinoia/ios/version.json`,
`tools/build-brand-icons.py` or the workflow:

1. **Checks** the plists and asset catalog JSON parse, the store icon is 1024 px with no alpha,
   `aps-environment` is `production`, and `version.json` has a positive integer `build` and an
   `x.y.z` `version`.
2. **Generates** the project: `brew install xcodegen` (if missing), `xcodegen generate` in `ios/`.
3. **Builds** an unsigned Release app for the simulator, then checks it carries version.json's
   numbers, the bundle ID, the privacy manifest and the icon. The app is attached to the run as
   **`ios-simulator-app`** (a zip; drag the `.app` onto a booted simulator on a Mac).
4. **Screenshots** the live site in the app in an iPhone Pro Max simulator: HOME, SLB fixtures, SLB
   stats and a team page, launched with `-EpinoiaStartURL <url>` (the app accepts only this site's
   pages there). Attached as **`ios-screenshots`**, even when a later step fails.
5. **Proves the `.p12` path**: a throwaway certificate exported with exactly the owner's OpenSSL 3
   flags (`-keypbe PBE-SHA1-3DES -certpbe PBE-SHA1-3DES -macalg sha1`) must import into a macOS
   keychain with the release step's own `security import`. OpenSSL 3's default `.p12` does not,
   and this finds out on the first run, not on release day.
6. **Releases**, only on `main`, only when all seven secrets are set, and only when the tag
   `ios-v<build>` does not exist yet: installs the certificate in a temporary keychain and the
   profile (checked: right App ID, production push, associated domains), archives with manual
   signing, exports **`ios-ipa`**, uploads it to App Store Connect (`xcrun altool --upload-app`, or
   `xcodebuild -exportArchive` with destination `upload` if altool is gone), and tags the commit
   `ios-v<build>`. The keychain, the profile and the API key are deleted at the end whatever happened.

Without the secrets, steps 1 to 5 still run, so a pull request proves the app compiles and renders
the site before the Apple account exists.

### The secrets

| secret | what it is |
|---|---|
| `IOS_DIST_CERT_P12_BASE64` | the Apple Distribution certificate and its private key, as a `.p12`, base64 on one line |
| `IOS_DIST_CERT_PASSWORD` | the password the `.p12` was exported with |
| `IOS_PROFILE_BASE64` | the App Store provisioning profile for `uk.co.prophesyscouting.epinoia` (with Push Notifications and Associated Domains), base64 |
| `IOS_TEAM_ID` | the 10-character Team ID (developer.apple.com > Account > Membership details) |
| `ASC_KEY_ID` | the App Store Connect API key's ID |
| `ASC_ISSUER_ID` | the API keys page's Issuer ID |
| `ASC_KEY_P8_BASE64` | the API key's `AuthKey_<ASC_KEY_ID>.p8` file, base64 |

How to make each one on the Windows PC, and set it, is in **docs/ios-app.md** (steps 2 and 5 to 9),
with the exact Command Prompt commands. Three things CI depends on:

- The `.p12` must be exported with `-keypbe PBE-SHA1-3DES -certpbe PBE-SHA1-3DES -macalg sha1`. The
  macOS keychain cannot read OpenSSL 3's default `.p12`; CI step 5 proves those flags on every run.
- The App ID must have **Push Notifications** and **Associated Domains** turned on **before** the
  App Store profile is generated. A profile made earlier lacks them; CI stops and names the missing
  one before archiving.
- The app record must exist in App Store Connect (docs/ios-app.md step 9): an upload for a bundle ID
  with no app is refused.

None of these files may ever be inside the repository folder (`ios/.gitignore` lists them anyway).

## Shipping a new version

Raise `build` in `epinoia/ios/version.json` (and `version`, for a version people see), and push to
`main`. App Store Connect refuses a build number it has already seen, and the workflow uploads a
build number only once (the `ios-v<build>` tag). Nothing else ships a build: an edit that only
changes `minShell` uploads nothing. The build then appears in TestFlight once Apple has processed
it, and goes to the App Store when submitted for review there.

The site asks the app to update when its `build` is below `minShell`.

## Opening it on a Mac

```sh
brew install xcodegen
cd ios
xcodegen generate
open Epinoia.xcodeproj
```

Run `xcodegen generate` again after pulling a change to `project.yml` or after adding a file to
`Epinoia/`. Never commit `Epinoia.xcodeproj`.

- In **Signing & Capabilities**, choose your team; automatic signing makes a development profile.
- **Push on a phone from Xcode**: a development profile's `aps-environment` is `development`, and
  `Epinoia.entitlements` says `production` for the store. Change it to `development` locally for
  that run and never commit it (CI refuses it). A DEBUG build reports `apnsEnv: 'sandbox'`, so its
  token is saved against APNs' sandbox.
- **Web Inspector**: DEBUG builds set `isInspectable`, so Safari's **Develop** menu shows the app's
  page on a simulator or a connected phone.
- **Another start page**: add `-EpinoiaStartURL https://prophesyscouting.co.uk/epinoia/...` under
  **Product > Scheme > Edit Scheme > Run > Arguments**.
